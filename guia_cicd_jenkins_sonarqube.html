01 El proyecto: Sistema de Notas Universitarias

El proyecto que analizaremos hoy es un gestor de notas universitario escrito en Python. Tiene tres módulos independientes con responsabilidades bien definidas, y 70 pruebas unitarias que verifican su comportamiento. Este es exactamente el tipo de proyecto que Jenkins y SonarQube están diseñados para proteger.

👨‍🎓

estudiantes.py

Gestión del registro de estudiantes. Validación de códigos, nombres y emails. Búsqueda, listado ordenado y eliminación.

21 pruebas
📚

materias.py

Registro de materias del plan de estudios. Validación de créditos (1–6), suma total de créditos, ordenamiento por nombre.

22 pruebas
📝

notas.py

Asignación de trabajos y cálculo de promedios. Notas entre 0.0 y 5.0, aprobación ≥ 3.0, reportes por estudiante.

27 pruebas
¿Por qué este proyecto? Tiene tres módulos con dependencias entre ellos (notas depende de estudiantes y materias), lo que hace que el análisis de SonarQube sea más interesante — detectará el acoplamiento, la cobertura por módulo y posibles problemas de calidad.

03 Anatomía del código fuente

Módulo 1 — estudiantes.py

Define dos clases: Estudiante (el modelo de datos) y RegistroEstudiantes (el repositorio en memoria). Observa cómo cada método valida sus entradas y lanza excepciones descriptivas.

Python src/estudiantes.py — fragmento clave 
class Estudiante:
    def __init__(self, codigo: str, nombre: str, email: str):
        if not codigo or not codigo.strip():
            raise ValueError("El código del estudiante no puede estar vacío.")
        if "@" not in email:
            raise ValueError("El email debe contener '@'.")

        self.codigo = codigo.strip().upper()   # siempre mayúsculas
        self.nombre = nombre.strip()
        self.email  = email.strip().lower()    # siempre minúsculas


class RegistroEstudiantes:
    def __init__(self):
        self._estudiantes: dict[str, Estudiante] = {}

    def registrar(self, estudiante: Estudiante) -> None:
        if estudiante.codigo in self._estudiantes:
            raise ValueError(f"Ya existe un estudiante con código {estudiante.codigo!r}.")
        self._estudiantes[estudiante.codigo] = estudiante

Módulo 3 — notas.py (el más complejo)

Depende de los módulos 1 y 2. Maneja la lógica de negocio: una nota debe estar entre 0.0 y 5.0, y se aprueba con ≥ 3.0 — igual que en el reglamento de la institución.

Python src/notas.py — fragmento clave 
from src.estudiantes import Estudiante
from src.materias    import Materia

class Trabajo:
    NOTA_MIN = 0.0
    NOTA_MAX = 5.0

    def __init__(self, estudiante: Estudiante, materia: Materia,
                 nombre_trabajo: str, nota: float):
        if not (self.NOTA_MIN <= nota <= self.NOTA_MAX):
            raise ValueError(f"La nota debe estar entre {self.NOTA_MIN} y {self.NOTA_MAX}.")
        self.nota = round(float(nota), 2)   # 2 decimales siempre

    def aprobado(self) -> bool:
        return self.nota >= 3.0           # criterio de aprobación


class GestorNotas:
    def promedio_estudiante(self, codigo: str) -> float:
        trabajos = self.trabajos_de_estudiante(codigo)
        if not trabajos:
            return 0.0
        return round(sum(t.nota for t in trabajos) / len(trabajos), 2)

Anatomía de una prueba unitaria

Observa el patrón Arrange → Act → Assert en cada test:

Python tests/test_notas.py — ejemplo comentado 
def test_promedio_estudiante_calculo_correcto(self, gestor, estudiante, materia, materia2):

    # ── ARRANGE: preparar los datos de prueba ──
    gestor.asignar(Trabajo(estudiante, materia,  "Parcial 1", 4.0))
    gestor.asignar(Trabajo(estudiante, materia2, "Parcial 2", 3.0))

    # ── ACT: ejecutar la acción que queremos probar ──
    promedio = gestor.promedio_estudiante("E001")

    # ── ASSERT: verificar el resultado esperado ──
    assert promedio == 3.5   # (4.0 + 3.0) / 2 = 3.5

Fragmentos clave del Jenkinsfile explicados

Jenkinsfile variables de entorno 
environment {
    // Nombre del proyecto en SonarQube — debe coincidir exactamente
    SONAR_PROJECT_KEY  = "notas-universitarias"

    // URL del contenedor SonarQube en la red Docker calidad-net
    // Jenkins lo alcanza por nombre porque ambos están en la misma red
    SONAR_HOST_URL = "http://sonarqube:9000"

    // Porcentaje mínimo de cobertura requerido
    COVERAGE_THRESHOLD = "80"
}
Jenkinsfile stage de pruebas con cobertura 
stage("3 · Pruebas unitarias") {
    steps {
        sh """
            python3 -m pytest tests/ \\
                --cov=src \\                        # mide cobertura del paquete src/
                --cov-report=xml:reports/coverage.xml \\  # XML para SonarQube
                --cov-report=html:reports/coverage_html \\ # HTML para Jenkins
                --cov-fail-under=\${COVERAGE_THRESHOLD} \\ # falla si < 80%
                --junitxml=reports/test_results.xml   # resultados para Jenkins
        """
    }
    post {
        always {
            // Publica resultados en el dashboard de Jenkins aunque fallen
            junit "reports/test_results.xml"
            publishHTML([...])   // reporte de cobertura visual
        }
    }
}

08 Interpretar los resultados en SonarQube

Una vez que el pipeline pase completamente, ve a http://localhost:9000 y abre el proyecto notas-universitarias. Estas son las métricas que debes saber interpretar:

Coverage — Cobertura

Porcentaje de líneas de código ejecutadas por las pruebas. El proyecto debería mostrar ~95% porque tiene 70 pruebas bien distribuidas. Una cobertura alta no garantiza que las pruebas sean buenas, pero una cobertura baja garantiza que hay código no verificado.

Bugs — Errores potenciales

Código que SonarQube identifica como probable fuente de errores en tiempo de ejecución. Para este proyecto debería ser 0 o cercano a 0.

Code Smells — Deuda técnica

Código que funciona pero que podría mejorar: métodos demasiado largos, variables sin usar, duplicación sutil. SonarQube estima el tiempo que tomaría corregirlos.

Duplications — Duplicación

Bloques de código idéntico o muy similar. Alta duplicación = más superficie para introducir bugs al cambiar lógica en un lugar y olvidar actualizarla en el otro.

El dashboard de cobertura por archivo

En SonarQube, haz clic en Code y luego en cada archivo de src/. Verás línea por línea cuáles están cubiertas (verde) y cuáles no (rojo). Para este proyecto, las líneas rojas deberían ser pocas porque el __repr__ a veces no es llamado directamente.

Reto 5 · Avanzado Introducir un code smell intencional

En src/notas.py, duplica el método promedio_estudiante creando un método idéntico llamado calcular_promedio. Vuelve a ejecutar el pipeline. ¿SonarQube detecta la duplicación? ¿El Quality Gate falla o solo registra una advertencia? ¿Cuánto tiempo de deuda técnica le asigna? Ver pista
SonarQube detecta bloques duplicados de más de 10 líneas por defecto. Un método duplicado de ~8 líneas puede o no activar el detector según la configuración. Si el Quality Gate no falla, busca la sección "Duplications" en el dashboard del proyecto — aparecerá como code smell aunque no bloquee el build. Esto ilustra la diferencia entre "falla el build" y "registra un problema".
