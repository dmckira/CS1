03 Módulo autenticacion.py — Vulnerabilidades críticas

Este módulo implementa el sistema de login. Fue desarrollado "con prisa" — un escenario muy común en equipos reales bajo presión de tiempo. Contiene 5 vulnerabilidades de distinta severidad.

Crítica

SQL Injection

python:S3649

La query de login concatena el username directamente. Un atacante puede ingresar ' OR '1'='1 y bypassear la autenticación.

Crítica

Hardcoded Credentials

python:S6437

La contraseña del admin y la clave secreta están escritas literalmente en el código fuente. Cualquiera con acceso al repositorio las ve.

Alta

Weak Hashing — MD5

python:S4790

MD5 es criptográficamente roto. Un atacante con la base de datos puede crackear las contraseñas con rainbow tables en segundos.

Alta

Token predecible (random)

python:S2245

random no es criptográficamente seguro. Un atacante puede predecir el siguiente token si conoce el estado del generador.

Media

Bare except / log a stdout

python:S110, S106

Capturar todas las excepciones oculta errores reales. Imprimir la excepción a stdout filtra información técnica al usuario final.

El código con las vulnerabilidades señaladas

⚠ Vulnerabilidades src/autenticacion.py — fragmentos críticos 
# [VULN CRÍTICA] Credenciales hardcodeadas — SonarQube: python:S6437
ADMIN_PASSWORD = "admin1234"          # ← expuesto en el repositorio
DB_SECRET_KEY  = "clave_secreta_123"  # ← expuesto en el repositorio

# [VULN ALTA] Hash débil — SonarQube: python:S4790
def _hash_password(password: str) -> str:
    return hashlib.md5(password.encode()).hexdigest()  # ← MD5 es débil

# [VULN CRÍTICA] SQL Injection — SonarQube: python:S3649
def login(username: str, password: str, db_path: str) -> dict:
    query = "SELECT * FROM usuarios WHERE username = '" + username + \
            "' AND password = '" + _hash_password(password) + "'"
    # Ataque: username = "' OR '1'='1"  →  acceso sin credenciales
    try:
        cursor.execute(query)
    except:                 # ← bare except — SonarQube: python:S110
        user = None

# [VULN ALTA] Token predecible — SonarQube: python:S2245
def generar_token_sesion(username: str) -> str:
    token = "".join(random.choice(chars) for _ in range(16))  # ← random no es seguro
    return f"{username}:{token}"
Reto 1 · Básico Identificar el ataque SQL Injection

La función login() construye la query así:
"SELECT * FROM usuarios WHERE username = '" + username + "'"

Si un atacante ingresa ' OR '1'='1' -- como username, ¿cómo quedaría la query completa? ¿Por qué eso le daría acceso sin saber la contraseña real?

Ver pista
La query resultante sería: SELECT * FROM usuarios WHERE username = '' OR '1'='1' --' AND password = '...'. La condición '1'='1' siempre es verdadera, y el -- comenta el resto. La base de datos retorna todos los usuarios y el primero se usa para "autenticar".

04 Módulo reportes.py — Code smells y bugs

Este módulo fue escrito con prisa por un desarrollador distinto — reutilizó código, no validó casos borde y eligió nombres que violan las convenciones del lenguaje.

Alta

División por cero

python:S3518

reporte_general() divide directamente por el número de estudiantes y materias sin validar que sean mayor a cero. Con registros vacíos, ZeroDivisionError.

Media

Código duplicado

common:DuplicatedBlocks

calcular_promedio_estudiante() es una copia exacta de GestorNotas.promedio_estudiante(). Viola DRY — si la lógica cambia en uno, el otro queda desactualizado.

Media

Complejidad cognitiva alta

python:S3776

GENERAR_REPORTE_CSV() tiene 4 niveles de anidación innecesarios. SonarQube penaliza la complejidad que dificulta la lectura y el mantenimiento.

Baja

Variable sin usar

python:S1481

FORMATO_FECHA, VERSION_REPORTE y resultado_sin_usar son declaradas pero nunca referenciadas. Código que confunde al lector.

Baja

Nombre de función en mayúsculas

python:S100

GENERAR_REPORTE_CSV viola PEP8. En Python, las funciones deben usar snake_case. Las mayúsculas se reservan para constantes.

El bug de división por cero — señalado

⚠ Bug src/reportes.py — función reporte_general 
def reporte_general(gestor, registro_est, registro_mat) -> dict:
    estudiantes = registro_est.listar()
    total_estudiantes = len(estudiantes)

    promedio_global = sum(
        gestor.promedio_estudiante(e.codigo) for e in estudiantes
    ) / total_estudiantes   # ← ZeroDivisionError si total_estudiantes == 0

    promedio_por_materia = sum(
        gestor.promedio_materia(m.codigo) for m in materias
    ) / total_materias      # ← ZeroDivisionError si total_materias == 0

    return {"promedio_global": round(promedio_global, 2), ...}
Reto 2 · Intermedio Calcular la complejidad cognitiva

Abre src/reportes.py y cuenta los niveles de anidación en GENERAR_REPORTE_CSV. SonarQube penaliza +1 por cada for, if, else anidado. ¿Cuántos puntos de complejidad tiene esta función? ¿Cómo la reescribirías para reducirla?

Ver pista
El bucle for es +1. Dentro, el primer if/else es +1. Dentro del if, otro if/else es +2 (nivel anidado). Dentro de ese, otro if/else es +3. Total: al menos 7 puntos. Una reescritura limpia reemplaza los 3 if anidados por: aprobados += 1 if t.nota >= 3.0 else 0 — la lógica de aprobado es binaria, no necesita sub-condiciones.

06 Aplicar las correcciones — Before / After

Corrección 1 — SQL Injection → Parámetros preparados

❌ Vulnerable
# Concatenación directa — SQL Injection
query = "SELECT * FROM usuarios " \
        "WHERE username = '" + username + \
        "' AND password = '" + pwd + "'"
cursor.execute(query)
✅ Corregido
# Parámetros preparados — seguro
query = "SELECT * FROM usuarios " \
        "WHERE username = ? AND password = ?"
cursor.execute(query, (username, pwd))

Corrección 2 — MD5 → bcrypt / SHA-256 con salt

❌ Débil — MD5
import hashlib
def _hash_password(pwd):
    return hashlib.md5(
        pwd.encode()
    ).hexdigest()
✅ Fuerte — SHA-256 + salt
import hashlib, secrets
def _hash_password(pwd: str) -> str:
    salt = secrets.token_hex(16)
    h = hashlib.sha256(
        (salt + pwd).encode()
    ).hexdigest()
    return f"{salt}${h}"

Corrección 3 — Credenciales hardcodeadas → Variables de entorno

❌ Expuesto en código
ADMIN_PASSWORD = "admin1234"
DB_SECRET_KEY  = "clave_123"
✅ Desde entorno
import os
ADMIN_PASSWORD = os.environ["ADMIN_PASSWORD"]
DB_SECRET_KEY  = os.environ["DB_SECRET_KEY"]

Corrección 4 — División por cero → Validación previa

❌ ZeroDivisionError
promedio_global = sum(
    gestor.promedio_estudiante(e.codigo)
    for e in estudiantes
) / total_estudiantes   # ← crash si 0
✅ Validado
if total_estudiantes == 0:
    promedio_global = 0.0
else:
    promedio_global = sum(
        gestor.promedio_estudiante(e.codigo)
        for e in estudiantes
    ) / total_estudiantes

Corrección 5 — Token aleatorio → secrets

❌ Predecible — random
import random, string
token = "".join(
    random.choice(chars)
    for _ in range(16)
)
✅ Criptográfico — secrets
import secrets
token = secrets.token_hex(32)
# 64 chars hex, imposible de predecir

07 Actualizar el pipeline para el Sprint 2

El Jenkinsfile del Sprint 1 ya cubre los nuevos módulos automáticamente porque usa -Dsonar.sources=src (escanea toda la carpeta) y python3 -m pytest tests/ (ejecuta todos los tests). No necesita cambios para el Sprint 2.

Sin embargo, es una buena práctica agregar una variable de entorno que identifique el sprint:

Jenkinsfile actualización recomendada 
environment {
    SONAR_PROJECT_KEY  = "notas-universitarias"
    SONAR_PROJECT_NAME = "Sistema de Notas Universitarias"
    SONAR_HOST_URL     = "http://sonarqube:9000"
    COVERAGE_THRESHOLD = "75"   # ← bajado temporalmente: Sprint 2 tiene módulos nuevos
                                   #   con menos cobertura. Subir a 80 en el Sprint 3.
    SPRINT             = "2"    # ← identificador del incremento
}
¿Por qué bajar el umbral temporalmente? Los módulos del Sprint 2 tienen pruebas básicas pero no cubren todos los paths de error (especialmente los de login() que requieren un SQLite real). Bajar el umbral a 75% durante este sprint es técnicamente honesto — y documentarlo en el Jenkinsfile comunica al equipo que es temporal.
